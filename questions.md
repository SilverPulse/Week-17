# Вопросы для самопроверки

1. Какие критерии вы использовали при разделении монолита на микросервисы (или при проектировании сервисов)?
-Single Responsibility Principle (функциональная ответственность).
-Разделение синхронного и асинхронного контуров.
-API Gateway → только маршрутизация и валидация.
-events-svc-s18 → управление сущностью «мероприятие» + БД.
-Уведомления → в отдельный асинхронный сервис (слабая связность: сбои в уведомлениях не ломают основной процесс).

2. Почему вы выбрали именно этот стек технологий (язык, БД, протоколы)?
-Python (FastAPI/gRPC) → скорость разработки, библиотеки.
-PostgreSQL → ACID, надёжность.
-REST (HTTP) → внешний интерфейс (API Gateway) — стандарт для фронтенда.
-gRPC (Protobuf) → межсервисное взаимодействие: строгий контракт, высокая скорость, низкие задержки.
-RabbitMQ → асинхронная связь, гарантия доставки.

3. Как ваши сервисы справляются с ошибками (retry, circuit breaker, graceful degradation)?
-API Gateway перехватывает grpc.RpcError → возвращает HTTP 500 (без аварийного завершения).
-Сервис уведомлений: retry с экспоненциальной задержкой (до 10 попыток, 3 сек) при инициализации RabbitMQ.
-Graceful degradation: при отказе уведомлений создание мероприятий продолжается (нет жёсткой синхронной привязки).

4. Как организован деплой и обновление вашей системы без простоя (Zero Downtime)?
Деплой автоматизирован через CI/CD пайплайн (например, GitHub Actions). При обновлении кода в ветке main робот собирает новый Docker-образ, тегирует его уникальным хешем коммита и отправляет команду в Kubernetes на обновление Deployment.

Zero Downtime (нулевой простой) достигается за счет стратегии Rolling Update и настройки Readiness Probes (проб готовности) в K8s.
Когда приходит новая версия сервиса, Kubernetes не удаляет старые контейнеры (поды) сразу. Он создает один новый под и ждет. Благодаря readinessProbe, K8s постоянно стучится в порт нового пода. Как только новый под отвечает, что он загрузился и готов работать, K8s переключает на него часть клиентского трафика. Только после этого K8s аккуратно завершает один старый под. Параметр maxUnavailable: 0 гарантирует, что система ни на секунду не останется без рабочих реплик, и пользователи вообще не заметят момента обновления.

5. Что было самым сложным в интеграции всех компонентов вместе?
-Согласование версий Protobuf (grpcio-tools vs protobuf) в Docker — помогла фиксация версий в requirements.txt.
-Race condition при холодном старте контейнеров (подключение к PostgreSQL/RabbitMQ до готовности портов) → решено программным ожиданием.

6. Что бы вы улучшили, если бы у вас был еще месяц?
-Наблюдаемость: Structured Logging + распределённый трейсинг.
-Отказоустойчивость: Circuit Breaker на шлюзе для gRPC.
-Тестирование: расширить покрытие, встроить автотесты в CI/CD.
